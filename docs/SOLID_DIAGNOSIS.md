## 3. Criterio para razonar sobre SOLID

Para SRP buscamos motivos independientes de cambio y a quién responde una regla; contar tareas, líneas o dependencias no identifica esa responsabilidad. Los roles del ejemplo teórico no se asignan al equipo. [Martin, The Single Responsibility Principle, 08/05/2014](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html).

Para DIP examinamos dependencias de fuente entre políticas y detalles, además de las llamadas en ejecución. Recibir una clase concreta por constructor no demuestra inversión; tampoco cualquier uso de Firebase constituye una infracción. [Martin, A Little Architecture, 04/01/2016](https://blog.cleancoder.com/uncle-bob/2016/01/04/ALittleArchitecture.html).

OCP requiere identificar una variación pertinente y qué código estable obliga a modificar. LSP requiere contrato común y una implementación que no lo respete al sustituirse. ISP requiere evidenciar dependencia del cliente en operaciones que no necesita. [Martin, Solid Relevance, 18/10/2020](https://blog.cleancoder.com/uncle-bob/2020/10/18/Solid-Relevance.html). En este recorrido no se acreditó una infracción OCP/LSP/ISP; no se inventa un problema para completar las cinco letras.

**Contraejemplos locales útiles:** SubmissionFactory.create agrupa construcción, conteos, UUID y timestamp de un mismo envío: no se declara SRP roto por esa lista. Sus dependencias de reloj/UUID pueden afectar caracterización, pero no prueban DIP por sí mismas. Los mappers aíslan conversiones, aunque su contrato pueda diferir del servidor (DG-02/06). Los when de modos cerrados y el switch de acciones no prueban OCP. Tener un repositorio amplio no basta para ISP. Un enum inválido no prueba LSP; tampoco que hoy falten implementaciones alternativas acredita cumplimiento universal de LSP.
